- 작성 기준일: 2026-08-28
- 문서 상태: **1차 초안 — 8장의 "미정" 항목은 아직 결정되지 않음, 임의로 구현하지 않는다**
- 관련 문서: `CLAUDE.md`(브랜치/네이밍/아키텍처 원칙), `docs/zippalgo360-db-architecture-guide.md`(목표 DB 구조),

- 적용 범위: 회원 유형, 가입/로그인, 하위 서비스 접근 통제, 관리자 화면 구조. DB 스키마 자체의 리팩터링은
  다루지 않는다(`zippalgo360-db-architecture-guide.md` 14장 참고, 로컬 서버 이전 완료 전에는 스키마 변경 안 함).

이 문서는 2026-08-28 대화에서 확정된 원칙과, 실제 코드(`apps/web/src/app`, `apps/api/app/modules`)를 대조

먼저 읽고, 이 문서와 다르게 판단할 경우 그 이유와 함께 이 문서를 갱신한다.

## 1. 회원 유형과 역할 모델

집팔고360은 **회원(가입/로그인)의 유일한 소유자**다. 하위 서비스(집팔고, 집테리어, 집서비스)는 자체 회원가입을
새로 만들지 않는다. (`CLAUDE.md` "회원/SSO/등급·결제 아키텍처" 절, 이미 확정)

역할은 현재 스키마 그대로 3단계를 유지한다 (`users.role`: `customer` / `company` / `admin`). 이 문서 시점에
스키마 변경은 없다.

### 1.1 일반회원 (`customer`)

- **모든 하위 서비스를 서비스별 추가 가입 없이 그대로 이용한다.** 집팔고 매물 조회, 집테리어 견적문의, 집서비스
  이사/청소 견적 요청 등은 전부 같은 `users.id`로 동작한다.
- 하위 서비스 쪽에서 "이 사람이 이 서비스를 쓸 수 있는가"를 별도로 심사하지 않는다 — 로그인돼 있으면 그것으로
  충분하다.
- 카카오 로그인은 일반회원 전용으로 이미 구현돼 있다 (`apps/api/app/modules/auth/kakao.py`,
  `apps/web/src/components/KakaoLoginButton.tsx`). 업체회원 가입 화면에는 카카오 로그인 버튼을 노출하지 않는다
  (`apps/web/src/app/register/page.tsx`가 이미 이렇게 돼 있음 — 유지).

### 1.2 업체회원 (`company`)

- 업체는 **하나의 영역(`company_type`)에만 속한다**는 것을 전제로 설계한다: `real_estate`(집팔고),
  `interior`(집테리어), `mover`/`cleaner`(집서비스). 한 업체가 여러 영역을 겸업하는 케이스는 2026-08-28
  대화에서 "거의 없을 것"으로 판단했고, 실제로 `companies` 테이블도 업체당 `company_type` 하나만 갖는
  구조로 이미 짜여 있다(`apps/api/app/modules/companies/schemas.py`).
- 이 전제가 스키마와 일치하므로, 목표 문서(`zippalgo360-db-architecture-guide.md` 14.2)가 제시하는
  `company_memberships`/`company_services`(다대다, 겸업 지원용) 구조는 **지금 도입하지 않는다.** 겸업
  케이스가 실제로 등장하면 그때 다시 판단한다.
- 업체회원은 `users.role = "company"`로 먼저 가입한 뒤, 온보딩 화면(`/onboarding/company`)에서 실제 업체
  정보(`companies` row)를 등록하는 2단계 구조다. `users`만 있고 `companies` row가 없는 상태(가입은
  했지만 업체 등록을 안 한 상태)가 존재할 수 있다는 뜻 — 화면/승인 로직에서 이 상태를 항상 고려한다.

**⚠️ 현재 구현 갭**: `apps/web/src/app/onboarding/company/page.tsx`는 `company_type: "real_estate"`를
하드코딩해서 전송한다. 즉 **지금 실제로 동작하는 업체가입은 집팔고(공인중개사)뿐**이고, 집테리어(interior)나
집서비스(mover/cleaner) 업체가 이 화면으로 가입하는 경로는 아직 없다. `register/page.tsx`의 역할 토글도
"일반회원 / 공인중개사(업체)" 두 가지뿐이라 같은 문제다. 집테리어·집서비스 업체가입을 이 SSO 체계로
받을지, 언제 받을지는 8장 미정 사항 참고.

### 1.3 관리자 (`admin`)

- 지금은 단일 등급이다 — `useRequireRole("admin")` 하나가 전체 `/admin/*`을 다 열어준다. 서비스별
  담당자를 구분하는 권한 체계는 아직 없다(5.4절 미정 사항).

## 2. 하위 서비스 접근 통제 규칙

| 회원 유형 | 집팔고 | 집테리어 | 집서비스 |
|---|---|---|---|
| `customer` | 항상 이용 가능 | 항상 이용 가능 | 항상 이용 가능 |
| `company` (`company_type=real_estate`) | 이용 가능 (매물 열람권한 등 결제 연동) | 접근 불가 | 접근 불가 |
| `company` (`company_type=interior`) | 접근 불가 | 이용 가능 | 접근 불가 |
| `company` (`company_type=mover`/`cleaner`) | 접근 불가 | 접근 불가 | 이용 가능 |

- 통제 시점은 **서비스 진입 시점(라우트 가드) + API 호출 시점(서버 측 권한 검사) 이중**으로 한다. 프론트
  라우트 가드만으로 끝내지 않는다 — `zippalgo360-server-architecture-guide.md` 27.2 "모든 API에서 서버 측
  authorization을 수행한다"와 동일 원칙.
- `customer`가 어떤 서비스든 열 수 있다고 해서 그 서비스 안의 개별 리소스(예: 특정 업체의 비공개 견적)까지
  다 볼 수 있다는 뜻은 아니다 — 이건 서비스별 리소스 권한 문제이지 이 문서의 범위가 아니다.

## 3. 가입/로그인 흐름

### 3.1 일반회원
1. `/register` (role=customer, 이메일+비밀번호) 또는 카카오 로그인
2. 가입 즉시 전 서비스 이용 가능, 별도 온보딩 없음

### 3.2 업체회원
1. `/register?type=company` (role=company, 이메일+비밀번호만 — 카카오 로그인 없음)
2. `/onboarding/company`로 리다이렉트 — 상호명/사업자등록번호/대표자명/주소/연락처/영업지역 입력
3. 제출 시 `POST /companies` 호출 → `companies` row 생성, `is_verified=false`
4. **집팔고360 Core 관리자**(`/admin/companies`)가 사업자등록번호 등을 확인해 승인(`verify`)/정지
   (`suspend`) 처리 — 4장·5.2절 참고
5. 승인 전에는 해당 서비스의 업체 전용 기능(매물 열람권한 판매 등)을 쓸 수 없다 (구체적 차단 로직은
   서비스별 구현 확인 필요 — 이 문서 작성 시점에 전수 검증 안 함)

### 3.3 로그인 공통
- `/login` — 이메일+비밀번호, JWT 발급 (`access_token`)
- 역할 무관 동일 로그인 화면/엔드포인트 사용 (`role`은 토큰과 `/auth/me` 응답에 포함)

## 4. SSO와 하위 서비스 연동

이미 구현된 흐름 (`apps/api/app/modules/auth/sso.py`, `router.py`):

1. 집팔고360에 로그인된 사용자가 하위 서비스(집테리어 등) 화면을 열 때, 프론트가
   `POST /auth/sso/issue-code`로 1회용·단기만료 코드 발급받음 (`SsoCodeOut`)
2. 하위 서비스는 이 코드를 URL로 받아, **자기 서버**에서 `POST /auth/sso/verify`를 호출해 코드 검증
   (`Authorization: Bearer {SSO_SHARED_SECRET}` — 서버 간 인증, 브라우저가 아님)
3. 응답으로 `user_id / email / name / role`을 받아 하위 서비스가 자기 쪽 계정을 찾거나 새로 만듦
4. 코드는 프로세스 메모리에만 저장(1회용, 만료됨) — 멀티 워커로 스케일하면 Redis 등으로 옮겨야 함
   (이미 코드 주석에 명시돼 있음, 지금은 uvicorn 단일 프로세스라 문제 없음)

**⚠️ 현재 구현 갭**: `CLAUDE.md`가 결정한 "`/auth/sso/verify` 응답에 등급(tier)·결제상태 필드를 포함시켜
하위 서비스가 그 자리에서 판단하게 한다"가 아직 반영 안 됨 — 지금 identity에는 `role`만 있고 tier/결제상태
필드가 없음. 결제/등급 기능이 실제로 생기기 전까지는 급하지 않음.

## 5. 관리자 체계

### 5.1 원칙

`CLAUDE.md`에 이미 결정된 원칙(재확인, 변경 없음): **회원 관리·결제 관리는 집팔고360 통합 관리자가 담당**,
**각 서비스 고유의 세부 운영은 해당 서비스 자체 관리자에 남긴다.** 집테리어 관리자를 다시 만들 필요 없음.

이걸 1~4장의 회원 모델에 대응시키면:

- **일반회원 관련 관리 업무**(활성화/비활성화, role 변경) → 서비스 무관, Core 관리자
- **업체 가입 심사(1차 게이트키핑, "이 사업자가 실존/신뢰 가능한가")** → 사업자번호 확인은 어느 영역이든
  본질적으로 같은 작업이라 Core 관리자에서 처리
- **승인된 업체의 서비스 내부 운영**(집팔고: 매물 검수·매도증빙 정산 / 집테리어: 포트폴리오 검수·견적 배정
  / 집서비스: 견적 배정·상품 관리) → 각 서비스 관리자

### 5.2 집팔고360 Core 관리자 (`apps/web/src/app/admin/*`)

지금 이미 구현돼 있는 화면과 소속 재확인:

| 화면 | 경로 | 소속 판단 |
|---|---|---|
| 회원 관리 | `/admin/members` | Core (맞음) |
| 업체 승인 관리 | `/admin/companies` | Core (맞음 — 전 영역 공통 게이트키핑) |
| 단지 마스터데이터 | `/admin/apartments` | Core (맞음 — 집팔고360이 소유하는 공유 마스터데이터, `CLAUDE.md` 아키텍처 원칙) |
| 매도증빙 검토(더블베네핏) | `/admin/sale-proofs` | **재분류 대상 — 실제로는 집팔고 전용 업무.** 지금 "서비스 공통 항목"이라는 admin 홈 문구 아래 같이 걸려 있지만, 성격상 5.3절 "집팔고 관리자" 영역 |

### 5.3 서비스별 관리자

- **집팔고 관리자**: 별도 legacy 시스템이 없다 — 이 저장소(`apps/web`)가 집팔고 자체 프론트이기도 하므로,
  같은 Next.js 앱 안에서 **메뉴/경로만 분리**하는 방식이 합리적이다(예: `/admin` 아래 "Core"/"집팔고" 섹션
  구분, 또는 `/admin/zippalgo/*` 서브경로). 별도 배포 단위로 쪼갤 필요는 없다 — 지금은 물리적 분리보다
  메뉴/권한상의 논리적 분리가 목적.
  - 매도증빙 검토(`/admin/sale-proofs`)를 여기로 재분류 (5.2절 참고, 실제 이동은 8장 미정 항목 결정 후)
  - 매물 검수 등 추가 업무는 실제 구현 여부 확인 후 채워나감
- **집테리어 관리자**: 기존 legacy 시스템(별도 코드베이스, `/srv/zipterior`) 그대로 유지. 이 저장소에서
  다시 만들지 않는다. 이관 대상 아님(6장 참고).
- **집서비스 관리자**: 이 저장소에 아직 없음. 집서비스 자체 기능(견적요청/쇼핑)이 실제로 얼마나 구현돼
  있는지부터 확인 후 필요성 판단.

### 5.4 관리자 권한 세분화 — 미정 (8장 참고)

서비스별 관리자가 늘어나면 "전체를 다 보는 슈퍼관리자"와 "자기 서비스만 보는 담당자"를 구분해야 하는
시점이 온다. 지금 `role="admin"` 하나로는 이 구분이 불가능하다. 지금 당장 운영 인력 규모상 필요한지
아닌지는 8장 참고.

## 6. 집테리어 기존회원/업체 이관

`CLAUDE.md`에 결정된 순서(재확인):

1. 집팔고360 회원가입/로그인/카카오/업체가입 구현 — **완료** (1.2절 갭 제외)
2. 집테리어와 SSO 연동 실제 검증 — **엔드포인트는 구현됨(4장), 실제 운영 트래픽으로 단대단 검증 여부는
   확인 필요**
3. 기존 집테리어 가입자를 집팔고360 통합회원으로 이관/매핑 — **스크립트 작성 완료
   (`apps/api/scripts/zipterior_migration/`), 아직 서버에서 실행 안 됨.** 이메일/카카오ID 매칭, 기존 계정
   있으면 스킵(덮어쓰기 없음), role은 전부 `customer` 고정, **업체 데이터는 다루지 않음**(집테리어 자체
   관리자가 계속 관리한다는 전제와 일치)
4. 집테리어 자체 회원가입/로그인 진입점 정리 — **아직 하면 안 됨.** 3번이 실행/검증되기 전에 진행 시
   기존 집테리어 회원이 로그인 불가 상태가 되는 사고로 이어짐(`CLAUDE.md` 명시)

**참고**: 최근 PC `/zipterior` → `/map?mode=interior` 리다이렉트 작업으로 그 화면에서 집테리어 자체
로그인/회원사/관리자 메뉴 진입점이 빠진 상태다(`docs/WORK_LOG.md` 2026-08-27 항목). 이건 4번 단계를
건드린 것과 사실상 같은 효과라 — 3번이 아직 실행 전인데 진입점만 먼저 빠진 상태. 8장에서 다룬다.

## 7. 현재 구현 상태 vs 목표 상태 요약

| 항목 | 상태 |
|---|---|
| 일반회원 가입/로그인/카카오 | ✅ 완료 |
| 업체회원 가입(집팔고=real_estate) | ✅ 완료 |
| 업체회원 가입(집테리어=interior, 집서비스=mover/cleaner) | ❌ 미구현 (하드코딩으로 막혀 있음) |
| SSO issue-code / verify | ✅ 완료 (등급/결제상태 필드는 미포함) |
| SSO 실사용 단대단 검증 | ❓ 미확인 |
| 집테리어 회원 이관 스크립트 | ✅ 작성 완료, ❌ 미실행 |

## 8. 미정 사항 — 다음에 결정할 것

**이 항목들은 이 문서 시점까지 결정되지 않았다. 다음 세션이 임의로 결론 내리지 말고, 아래 각 항목을
사용자와 확인한 뒤 이 문서를 갱신하고 진행한다.**

1. **집테리어/집서비스 업체가입을 이 SSO 체계로 언제 받을 것인가.** 지금 당장은 집테리어 업체는 자기
   시스템에 그대로 있고(이관 대상 아님), 집서비스 업체는 아직 없음. 신규 집테리어/집서비스 업체가
   생기면 어디로 가입시킬지 아직 안 정함.
2. **PC `/map?mode=interior`에서 빠진 집테리어 자체 로그인/회원사 메뉴를 어떻게 복구할지** — 집팔고360
   로그인으로 대체할지, 당장은 보류할지(6장 참고, 지난 대화에서 사용자가 답변을 보류함).
3. **관리자 권한 세분화가 지금 필요한 수준인지** — 운영 인력 규모에 달려 있음.
4. **매도증빙 검토 화면을 실제로 "집팔고 관리자" 섹션으로 옮길지, 언제 옮길지** (5.2절 재분류 판단은
   내렸지만 실제 코드 이동은 별도 작업).
5. **업체가 여러 영역을 겸업하는 케이스가 실제로 발생하면** `company_memberships`/`company_services`
   전환을 검토한다는 전제 — 지금은 "거의 없다"는 가정으로 진행 중, 이 가정이 깨지면 재논의.
